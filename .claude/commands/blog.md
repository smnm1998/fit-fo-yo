# /blog — 페어 포스팅 세션

인자: **$ARGUMENTS**

## 0. 준비 (매번)

아래 두 문서를 읽고 시작한다. **지침이 이 커맨드보다 우선한다.**

@.claude/rules/blog-posting.md
@.claude/blog/README.md

## ⛔ 세션 규칙 (요약 — 상세는 지침 2절)

1. **② 백지 구술 전에는 초본도, 코드 설명도 내놓지 않는다.** 이 순서만은 예외 없다.
2. 초본에는 **빈칸 마커 `[[본인 설명 필요: …]]` 를 최소 3개** 심는다.
   결정 이유 · 포기한 것 · 당시 제약 · **실측 수치** · "지금 다시 한다면" → 절대 추측해서 채우지 않는다.
3. **한 응답에 여러 단계를 몰아 진행하지 않는다.** 각 단계 끝에서 응답을 끝내고 입력을 기다린다.
4. 틀린 사실은 **즉시 정확히 교정한다** (파일 경로:줄번호 첨부).
5. **git 명령을 직접 실행하지 않는다.** 브랜치명·커밋 단위·메시지·PR 본문을 제시만 한다.

## 모드 분기

`$ARGUMENTS` 를 보고 아래로 간다. **인자가 없거나 `pick` 이면 A.**

### A. 소재 고르기 (`/blog`, `/blog pick`)

1. `date "+%Y-%m-%d (%a)"` 로 요일 확인 → 백로그 **주간 리듬** 표에서 오늘 권장 유형 확인.
2. 미완료(`[ ]`) 중 오늘 유형·난이도에 맞는 **3개** 선정. 최근 발행분과 섹션이 겹치지 않게.
   "첫 2주 추천 순서"가 안 끝났으면 그 순서를 우선한다.
3. 이 형식으로 제시한다. **결정은 사용자가 한다.**

   ```
   오늘(수)은 A 설계 결정형 차례입니다.

   1. #03 BFF 패턴을 고른 이유와 그 대가 (⭐면접, ⭐⭐)
      → 이력서 카드. 근거: apps/web/lib/server/api.ts, proxy.ts
   2. #29 Zustand 스토어를 4개로 나눈 기준 (⭐⭐)
      → 최근에 만진 코드라 기억이 살아있을 때
   3. #35 안 만든 것: 디바운스를 규칙에만 두고 구현 안 한 이유 (⭐)
      → 시간 없을 때. 30분컷
   ```

4. **⛔ 응답 종료.** 번호를 고르면 B로.

### B. 백지 구술 (`/blog 15`)

1. 백로그에서 제목·타입·근거 파일을 확인한다. **근거 파일은 아직 열지 않는다.**
2. 이렇게 연다:

   ```
   #15 LLM 산수를 믿지 않기 (2) — 영양 DB grounding · 타입 D(성능·측정형)

   코드 열지 마세요. 기억나는 대로 3~5문장으로 설명해주세요.

   - 무슨 문제였고
   - 어떻게 해결했고
   - 그래서 숫자가 어떻게 바뀌었는지

   막히면 "여기 기억 안 남"이라고 그대로 적어주세요. 그 자리가 오늘 메울 지점입니다.
   (5분이면 됩니다. 이거 끝나면 제가 초본 씁니다.)
   ```

3. **⛔ 응답 종료.** 구술이 오면 C로.

### C. 초본 작성 (구술을 받은 뒤)

**한 응답에 이 순서로 낸다.**

1. **구술 채점 먼저 (짧게)** — 근거 파일을 열어 대조한다.
   - ✅ 맞음: 한 줄 확인만. 길게 칭찬하지 않는다.
   - ❌ 틀림: 정확히 교정 + `파일:줄번호`. 예 — "`resolveGrams`는 g/ml일 때만 LLM 그램수를 신뢰합니다 (`ai.service.ts:266-278`)"
   - ⬜ "기억 안 남": 여기만 설명한다.
2. **초본을 마크다운 파일로 쓴다** — 경로 `.claude/blog/drafts/<번호>-<슬러그>.md`
   - 해당 타입의 템플릿(지침 3절)을 소제목으로 사용
   - 1인칭, 사용자 문체. 과장 형용사 금지
   - 코드 인용 3~15줄 + 경로 캡션
   - **빈칸 마커 최소 3개** — 특히 수치·이유·대가
   - 전문용어 첫 등장 한 줄 풀이
3. 파일 경로를 알려주고 **채워야 할 마커 목록만** 요약한다.

   ```
   초본: .claude/blog/drafts/15-nutrition-grounding.md (1,900자)

   채워주셔야 할 곳 4군데:
   1. [[불닭 4000kcal → 1061kcal, 이 수치 어디서 확인한 건가요? 로그? 화면?]]
   2. [[시드 데이터를 몇 개 넣었고 무슨 기준으로 골랐나요?]]
   3. [[음식 DB API를 안 쓰고 직접 시드한 이유]]
   4. [[지금 다시 한다면 — 시드 방식 유지하실 건가요?]]
   ```

4. **⛔ 응답 종료.**

### D. 같이 수정 (사용자가 마커를 채워온 뒤)

1. 채워진 내용을 초본에 반영해 Edit 한다. **사용자 표현을 최대한 살린다** — 매끄럽게 다듬는다고 목소리를 지우지 않는다.
2. 반영 중 **4절 위반(근거 없는 수치)** 이 있으면 그 자리에서 지적하고 뺄지 묻는다.
3. 남은 마커가 있으면 지침 2절 **질문 카드**로 한 번 더 끌어낸다.
4. 마커가 다 채워졌으면 E로 넘어갈지 묻는다.

   ```
   본문 정리됐습니다 (2,300자). 마커 0개.
   이제 이 글의 근거 코드를 같이 리뷰할까요? (⑤단계, 15분)
   ```

5. **⛔ 응답 종료.**

### E. 코드 리뷰 (⑤)

**백로그의 근거 파일만** 본다. 옆길 금지 (스코프 확장 금지).

1. 근거 파일 전체를 읽는다 (일부만 보고 판단하지 않는다).
2. 발견 사항을 **등급별로** 낸다. 없으면 "없다"고 말한다 — 억지로 만들지 않는다.

   | 등급             | 뜻                          | 처리                            |
   | ---------------- | --------------------------- | ------------------------------- |
   | 🔴 버그·잠재버그 | 조건 맞으면 실제로 깨짐     | 오늘 고친다                     |
   | 🟡 설계 부채     | 지금은 동작, 확장 시 무너짐 | 30분 안이면 오늘, 아니면 백로그 |
   | 🟢 취향          | 네이밍·포맷·미세 최적화     | 고치지 않는다                   |

3. 각 항목은 이렇게 쓴다 — **어떤 조건에서 어떻게 깨지는지**를 반드시 포함:

   ```
   🔴 CalendarWorkspace.tsx:94-98 — 떠나는 달 스냅샷 저장이 changeMonth 안에만 있음
      goToday()가 같은 달일 때는 changeMonth를 안 타서 스냅샷이 저장되지 않음.
      → 조건: 3월에서 낙관적 추가 → '오늘'(3월) 클릭 → 4월 이동 → 3월 복귀 시 …

   🟢 STYLES 상수 네이밍이 일부 S로 되어 있음 → 오늘은 건드리지 않음
   ```

4. **⛔ 응답 종료.** 무엇을 고칠지는 사용자가 정한다.

### F. 수정 → 커밋 (⑥, 고칠 게 있을 때만)

1. **이유를 먼저 확정한다.** 코드보다 먼저 이 두 줄을 쓴다:

   ```
   문제: (증상 또는 잠재 위험)
   왜 지금 고치나: (안 고치면 언제 터지나)
   ```

   이 문장이 그대로 글의 「쓰다가 고친 것」 절이 된다.

2. **수정 코드를 완전한 형태로 출력한다.** 타이핑은 사용자가 한다.
   - 변경 전/후를 나란히, 바뀐 이유를 줄 단위로 설명
   - 테스트에 영향 있으면 spec mock 갱신까지 함께 (`.claude/trouble/14-…` 재발 방지)

3. **git은 제시만 한다. 실행하지 않는다.** 아래를 출력:

   ```markdown
   # 브랜치 (develop에서 분기)

   fix/calendar-snapshot-on-today

   # 커밋 메시지

   fix(web): goToday에서 월 스냅샷이 누락되는 경로 수정

   ## Changes

   - `changeMonth` 밖에 있던 스냅샷 저장을 …

   ## Notes

   - 블로그 #36 집필 중 발견

   # PR 본문 (base: develop, squash merge)

   ## Summary

   …

   ## Verification

   - [ ] pnpm lint && pnpm typecheck && pnpm test
   - [ ] 3월 낙관적 추가 → 오늘 → 4월 → 3월 복귀 재현 확인
   ```

4. 검증 명령을 안내한다: `pnpm lint && pnpm typecheck && pnpm test`, 필요시 `/code-review`.
5. squash merge 후에는 **브랜치 삭제 + 다음 작업은 develop에서 새 분기** 라고 알린다
   (`.claude/trouble/08-…`, `13-…` 재발 방지).
6. **⛔ 응답 종료.** 머지가 끝나면 G로.

### G. 마무리 (⑦)

1. 초본에 **「쓰다가 고친 것」** 절을 추가한다 (before/after + 이유 + 커밋/PR 링크).
2. **면접 질문 3개는 사용자가 먼저 뽑게 한다.** AI는 빠진 각도만 지적한다.
3. **발행 전 리뷰** — 지침 8절 체크리스트를 훑고 아래 5가지를 점검한다:

   | 검사    | 기준                                           |
   | ------- | ---------------------------------------------- |
   | 🔴 마커 | `[[…]]` 가 하나라도 남았으면 발행 금지         |
   | 🔴 수치 | 실측인가? Before→After + 측정 환경 있나?       |
   | 🟡 용어 | 전문용어 첫 등장 풀이 (BFF·MET·RTT·hydration…) |
   | 🟡 과장 | "혁신적/완벽한/압도적", 근거 없는 단정         |
   | 🟢 구조 | 코드 인용 3~15줄, 경로 캡션, 분량              |

4. **Cold drill** 을 시킨다 — 코드 닫고 핵심 블록 재작성, 막힌 줄 수 기록.
5. **⛔ 응답 종료.** 발행 후 `/blog done <번호> <링크>` 안내.

### H. 리뷰만 (`/blog review` + 초안 붙여넣기)

G-3의 5가지 검사만 수행한다. **다시 써주지 않는다** — 고칠 위치와 이유만 짚는다.

### I. Cold Drill 채점 (`/blog drill <번호>`)

1. 핵심 코드 블록(10~30줄)이 어디인지 알려주고 **닫으라고 한다.**
2. 재작성본을 원본과 대조한다. **동작이 달라지는 것만** 오답 — 표현 차이는 통과.
3. `막힌 줄 수 / 전체 줄 수 + 막힌 지점` 으로 요약하고 백로그 **Cold Drill 기록** 표에 Edit로 행 추가.
4. 이전 기록이 있으면 비교: "3주 전 6줄 → 오늘 2줄. `inflight` dedup은 이제 나옵니다."

### J. 발행 기록 (`/blog done <번호> [링크]`)

1. `.claude/blog/README.md` 해당 행을 `[x]` 로 바꾸고 발행일·링크를 붙인다.
2. ⑥에서 커밋이 나왔으면 백로그 하단 **코드 개선 로그** 표에 행을 추가한다.
3. 새로 발견한 부채가 있으면 백로그 신규 소재로 등록할지, `.claude/trouble/` 노트를 쓸지 묻는다.
4. 남은 미완료 편수 + 다음 추천 소재 1개를 알려주고 끝낸다.

## 소재가 떨어졌을 때

1. `.claude/trouble/` 중 아직 글이 안 된 노트 → 타입 B로 바로 나온다.
2. `git log --oneline -30` 에서 **사용자가 설명 못 하는 커밋** → 그게 감 빠진 지점이다.
3. 오늘 짠 코드를 타입 C로 정리.
4. 이전 세션 ⑤에서 미룬 🟡 부채 → 그 자체가 소재다.

새 소재를 만들면 백로그 표에 행을 추가한다 (번호 이어서).
