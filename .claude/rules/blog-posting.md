# ✍️ Blog Posting Rules (페어 포스팅 지침)

이 문서는 **매일 1편 블로그 포스팅**을 AI와 페어로 진행할 때의 규칙이다.
세션은 `/blog` 커맨드로 시작하고, 소재 목록은 `.claude/blog/README.md`(백로그)에 있다.

## 0. 목적 (왜 쓰는가)

1. **코드 감 유지** — 구현한 지 오래된 영역도 설명할 수 있는 상태로 되돌린다.
2. **코드 개선** — 글을 쓰려고 다시 읽으면 반드시 고칠 게 나온다. 그걸 **실제로 고치고 커밋**한다.
3. **사고력 훈련** — "왜 그렇게 했나"를 스스로 언어화한다.
4. **면접 답변 자산화** — 글 1편 = 면접 질문 1~3개에 대한 30초 답변.

> 목적 2가 이 루틴의 진짜 값어치다. **블로그가 리팩토링을 끌고 온다.**
> 글은 결과물이고, 남는 건 커밋과 설명할 수 있는 상태다.

## 1. 세션 흐름 (7단계)

| 단계               | 담당       | 내용                                             | 시간   |
| ------------------ | ---------- | ------------------------------------------------ | ------ |
| ① 소재 확정        | 사용자     | 백로그에서 1개 선택 (AI는 3개 추천까지)          | 3분    |
| ② **백지 구술**    | **사용자** | **코드 열기 전에** 기억만으로 3~5문장            | 5분    |
| ③ 초본 작성        | AI         | 구술 + 실제 코드 근거로 초본. **빈칸 마커 포함** | 5분    |
| ④ 같이 수정        | 함께       | 빈칸 채우기, 구조·톤 조정, 사실 확정             | 15분   |
| ⑤ **코드 리뷰**    | 함께       | 이 소재의 근거 코드를 지금 눈으로 다시 본다      | 15분   |
| ⑥ 코드 수정 → 커밋 | 사용자     | 고칠 게 있으면 **이유 먼저 적고** 수정·커밋·PR   | 0~30분 |
| ⑦ 마무리           | 함께       | 고친 이유를 글에 추가, 면접 Q, 백로그 기록       | 10분   |

**총 50분(수정 없는 날) ~ 80분(수정한 날).** 넘어가면 다음날 못 쓴다.
⑥에서 고칠 게 클 것 같으면 **그 자리에서 고치지 말고** 백로그에 부채로 적어두고 넘어간다.

### ② 백지 구술을 초본보다 먼저 하는 이유

초본을 먼저 보면 "읽고 고치기"(인식)가 되고, 기억에서 먼저 꺼내면 "인출"이 된다.
**감이 빠진 지점은 인출을 시도해야만 드러난다.** 5분이면 되고, 여기서 막힌 자리가
③~⑤에서 무엇을 집중적으로 볼지 정해준다. 이 순서만은 바꾸지 않는다.

### ③ 초본에 빈칸 마커를 심는다

AI 초본은 **코드에서 읽어낼 수 있는 것**까지만 쓴다. 그 외는 마커로 비운다.

```markdown
## 왜 Map 캐시였나

인접 월 프리페치는 …(코드로 확인되는 동작 서술)…

> [[본인 설명 필요: SWR·TanStack Query 같은 캐시 라이브러리를 안 쓰고
직접 Map을 든 이유 — 의존성 무게? 제어권? 그냥 학습 목적?]]
```

**마커를 반드시 심어야 하는 항목 (AI가 채우면 안 되는 것):**

- 결정의 **결정적 이유** — 코드에는 결과만 남고 이유는 안 남는다
- **포기한 것 / 대가** — 본인만 안다
- **당시 제약** (시간, 비용, 실력, 마감)
- 실측 **수치와 측정 환경** — 안 잰 걸 AI가 채우면 그게 곧 거짓말
- "지금 다시 한다면" 판단

최소 3개. 사용자가 "모르겠다"고 하면 그때 AI가 질문으로 끌어낸다(→ 2절 질문 카드).

## 2. AI 역할 규칙

### 해야 하는 것

- ✅ **초본을 쓴다.** 단 ② 이후에. 1인칭, 사용자 문체 기준.
- ✅ **틀린 사실은 즉시, 정확히 교정한다.** 파일 경로:줄번호를 붙인다.
- ✅ 코드 리뷰에서 개선점을 **분류해서** 낸다 (🔴 버그 / 🟡 설계 부채 / 🟢 취향).
- ✅ 사용자가 놓친 **대안**을 환기한다. → "Redis 캐시는 왜 안 썼나요?"
- ✅ 커밋 단위·메시지·PR 본문을 **제시**한다.

### 하면 안 되는 것

- ❌ ② 이전에 초본이나 코드 설명을 먼저 내놓기
- ❌ 빈칸 마커 항목을 AI가 추측해서 채우기 (특히 수치)
- ❌ 실측 안 된 수치·사용자 반응·성능 개선율 만들어내기 (→ 4절)
- ❌ 소재를 사용자 대신 고르기 (추천 3개까지, 결정은 사용자)
- ❌ **git 명령 직접 실행** — 커밋/푸시/머지는 사용자가 한다 (→ 6절)

### 질문 카드 (빈칸이 안 채워질 때 AI가 던지는 질문)

1. **왜 이 선택?** — 다른 방법도 됐을 텐데 이걸 고른 결정적 이유 하나는?
2. **대안은?** — 후보에 뭐가 있었고, 왜 탈락했나?
3. **안 했으면?** — 이 코드가 없으면 어떤 증상이 사용자에게 보이나?
4. **근거는?** — 그 숫자/판단은 어디서 나왔나? 재현할 수 있나?
5. **대가는?** — 이 선택으로 무엇을 포기했나? 지금도 같은 선택을 하겠나?
6. **경계는?** — 언제부터 이 방식이 무너지나? (데이터 10배, 사용자 100명 등)

## 3. 글 유형별 구조 템플릿

소재마다 유형이 정해져 있다(백로그 `타입` 열). AI 초본은 이 구조를 따른다.

### A. 설계 결정형 (Decision)

```
1. 무슨 문제였나        — 사용자에게 보이는 증상/요구
2. 제약 조건            — 개인 프로젝트, 비용, 배포 환경, 마감   [[마커]]
3. 후보 2~3개
4. 고른 것과 결정적 이유 — 이유는 1개로 좁힌다                  [[마커]]
5. 포기한 것 (대가)      — 없으면 결정이 아니라 취향             [[마커]]
6. 지금 다시 한다면                                            [[마커]]
```

### B. 트러블슈팅형 (Trouble)

`.claude/trouble/*.md` 포맷을 그대로 재사용한다.

```
1. 증상 (에러 메시지 원문 포함 — 검색 유입용)
2. 처음 세운 가설과 오진   — 틀린 길도 쓴다. 여기가 제일 재밌는 부분  [[마커]]
3. 진단 과정 (계층 격리)
4. 진짜 원인
5. 해결 코드
6. 예방 / 재발 방지
```

### C. 개념 정리형 (Concept)

```
1. 한 줄 정의 (비전공자도 이해할 말로)
2. 내 코드 어디에 쓰였나 — 파일 경로 + 3~15줄 인용
3. 안 쓰면 뭐가 문제인가
4. 흔한 오해 / 내가 헷갈렸던 것                                 [[마커]]
```

### D. 성능·측정형 (Measure)

```
1. 가설 — 여기가 느릴 것이다
2. 측정 방법 — 도구, 환경(dev/prod), 반복 횟수까지 명시          [[마커]]
3. Before 수치                                                 [[마커]]
4. 조치
5. After 수치                                                  [[마커]]
6. 한계 — 측정 안 한 것, 이 수치가 안 통하는 조건
```

### 공통 마지막 절 — 「쓰다가 고친 것」 (⑥이 있었던 날만)

````markdown
## 쓰다가 고친 것

글을 쓰려고 이 코드를 다시 읽다가 문제를 하나 발견했다.

**문제**: (증상 또는 잠재 위험)
**왜 고쳐야 하나**: (안 고치면 언제 터지나)

```ts
// before
```
````

```ts
// after
```

커밋: `fix(web): …` ([#PR번호])

````

이 절이 이 루틴의 결과물이다. **면접에서 그대로 쓴다.**

## 4. 사실·수치 규칙 (엄격)

- **실측하지 않은 수치는 쓰지 않는다.** "약 3배 빨라졌다" 같은 체감 표현 금지.
- 수치를 쓸 땐 **Before → After + 측정 환경**을 함께 쓴다.
  - ✅ "prod 기준 월 이동 시 캐시 미스 500~640ms → 캐시 히트 시 네트워크 요청 0회"
  - ❌ "월 이동이 2~3초에서 즉시로 개선"  ← 체감치, 실측 아님
- 없는 것은 **없다고 쓴다.** "사용자 반응", "동시접속", "부하 테스트 결과"를 지어내지 않는다.
- **AI는 수치를 초본에 채우지 않는다.** 반드시 `[[마커]]`로 비우고 사용자에게 묻는다.
- 재현 절차를 못 쓰겠으면 그 수치는 글에서 뺀다.

## 5. 문체 규칙

- **전문용어는 첫 등장에서 한 줄 풀이.**
  - "Function Calling(모델이 정해진 함수 목록 중 무엇을 호출할지 골라주는 기능)"
  - BFF, MET, RTT, 인출, hydration 전부 동일 적용.
- 과장 형용사 금지 — "혁신적", "완벽한", "압도적". 사실만으로 충분하다.
- 코드 인용은 **3~15줄.** 파일 전체를 붙이지 않는다. 경로를 캡션으로 단다.
- 분량 목표 **공백 포함 1,500~2,500자.** (「쓰다가 고친 것」 포함 시 3,000자까지)
- 1인칭("나는 ~했다")으로 쓴다. 결정한 사람이 쓰는 글이다.
- 흐름이 3단계 이상이면 ASCII 다이어그램 또는 mermaid 1개.

## 6. 코드 리뷰 · 수정 단계 (⑤~⑥)

### ⑤ 리뷰 범위

백로그의 **근거 파일**만 본다. 옆길로 새지 않는다 (스코프 확장 금지).

AI는 발견 사항을 이렇게 분류해서 낸다:

| 등급 | 뜻 | 처리 |
| --- | --- | --- |
| 🔴 버그·잠재버그 | 조건 맞으면 실제로 깨짐 | **오늘 고친다** |
| 🟡 설계 부채 | 지금은 동작하나 확장 시 무너짐 | 30분 안이면 오늘, 아니면 백로그로 |
| 🟢 취향 | 네이밍·포맷·미세 최적화 | **고치지 않는다** (커밋 노이즈) |

### ⑥ 수정 규칙

1. **이유를 먼저 쓴다.** 코드를 건드리기 전에 "왜 고치는가"를 한 줄로 적는다.
   그 문장이 그대로 글의 「쓰다가 고친 것」 절이 된다.
2. 코드는 **사용자가 직접 타이핑**한다. AI는 완전한 코드 + 상세 설명을 출력한다.
3. **git 명령은 사용자가 실행한다.** AI는 아래를 제시만 한다:
   - 브랜치명 — `fix/*` 또는 `refactor/*` (`.claude/rules/git-workflow.md`)
   - 커밋 단위 — 논리 단위로 분리, 거대 커밋 금지
   - 커밋 메시지 — `type(scope): message` + 마크다운 본문
   - PR 본문 — Summary / Changes / Verification
4. 흐름: `develop`에서 분기 → 수정 → PR → CI 통과 → **squash merge** → 브랜치 삭제 →
   **다음 작업은 develop에서 새로 분기** (squash한 브랜치 재사용 금지)
5. 검증: `pnpm lint && pnpm typecheck && pnpm test`. 필요하면 `/code-review` 로 한 번 더.

## 7. 필수 부록 2종 (모든 글 하단)

### ① 면접 예상 질문 3개 + 30초 답변

**사용자가 먼저 뽑는다.** AI는 빠진 각도만 지적한다. 답변은 말로 30초(3~4문장).

```markdown
> **Q. 왜 LLM이 계산한 칼로리를 그대로 안 쓰셨나요?**
> A. 언어 모델은 산수에서 자릿수를 자주 틀립니다. 실제로 불닭볶음면 한 봉지를
> 4000kcal로 잡은 적이 있었고요. 그래서 모델에겐 "음식명과 100g당 칼로리, 환산 그램"만
> 뽑게 하고 곱셈은 서버에서 했습니다. 등록된 음식은 DB 값으로 확정하고,
> 없는 음식만 모델 값을 쓰되 화면에 '추정' 배지를 붙였습니다.
````

### ② Cold Drill (인출 연습)

발행 후 **코드를 닫고** 5~10분 안에 핵심 코드를 백지에서 다시 써본다.
막힌 줄 수만 기록: `Cold drill: 22줄 중 6줄 막힘 — inflight dedup 부분`.
이게 "감 잃지 않기"의 실제 측정치다. 2~3주 뒤 같은 소재로 재측정한다.

## 8. 발행 후 체크리스트

- [ ] 빈칸 마커 `[[…]]` 전부 채워짐 (남아 있으면 발행 금지)
- [ ] 4절 위반(근거 없는 수치) 없음
- [ ] 전문용어 첫 등장 풀이 완료
- [ ] 코드 인용에 파일 경로 캡션 있음
- [ ] ⑥이 있었으면 「쓰다가 고친 것」 절 + 커밋 링크 포함
- [ ] 면접 질문 3개 + Cold drill 기록 작성
- [ ] `.claude/blog/README.md` 에 `[x]` + 발행일 + 링크, **코드 개선 로그** 행 추가

## 9. 소재가 떨어졌을 때

1. `.claude/trouble/` 에 아직 글이 안 된 노트 → 유형 B로 바로 나온다.
2. `git log --oneline -30` 에서 설명 못 하는 커밋 → 그게 감 빠진 지점이다.
3. **오늘 짠 코드**를 유형 C로 정리 (당일 소재가 가장 잘 써진다).
4. 이전 세션 ⑤에서 백로그로 미룬 🟡 부채 → 그 자체가 소재다.
